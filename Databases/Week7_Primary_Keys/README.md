## What a primary key is

A column — or a group of columns — that uniquely identifies a row. Four rules:

* **unique** — no two rows share a value
* **not null** — never empty
* **immutable** — not meant to change once assigned
* **one per table** — a table has exactly one primary key (which may span several columns)

It matters for four reasons: rows stay individually addressable, foreign keys
have something to point at (referential integrity), PostgreSQL builds a unique
B-tree index that makes lookups and joins fast, and replication needs a stable
row identity.

## Three ways to declare one

| Method | Where | Constraint name |
|---|---|---|
| column-level | `student_id INTEGER PRIMARY KEY` | `students_pkey` (auto) |
| table-level | `PRIMARY KEY (student_id)` | `students_pkey` (auto) |
| named | `CONSTRAINT pk_students PRIMARY KEY (student_id)` | `pk_students` |

The result is identical — `\d` shows the same index on all three. Only the
third gives the constraint a name you chose, which is what you need when you
later want to drop or reference it.

On a table that already exists:

```sql
ALTER TABLE no_key ADD CONSTRAINT pk_no_key PRIMARY KEY (student_id);
```

## Single vs composite

A single key is one column — `student_id SERIAL PRIMARY KEY`.

A composite key is several columns together, used when no single column is
unique. In `course_enrollments` a student takes many courses, a course has
many students, and both repeat every semester, so the key is all three:

```sql
PRIMARY KEY (student_id, course_id, semester)
```

That is why `(1, 101, '2024-Spring')` and `(1, 101, '2024-Fall')` can coexist —
same student, same course, different semester. Repeating all three fails:

```
ERROR:  duplicate key value violates unique constraint "course_enrollments_pkey"
DETAIL:  Key (student_id, course_id, semester)=(1, 101, 2024-Spring) already exists.
```

## Auto-generated keys

PostgreSQL has no `AUTO_INCREMENT`. Four options instead:

| | What it is |
|---|---|
| `SERIAL` | `INTEGER` + a sequence + `DEFAULT nextval(...)` — `\d` shows the default |
| `BIGSERIAL` | the same with `BIGINT`, for tables that outgrow 2.1 billion rows |
| `GENERATED ALWAYS AS IDENTITY` | PostgreSQL owns the value; supplying one is an error |
| `GENERATED BY DEFAULT AS IDENTITY` | generated unless you supply a value |

The difference between the two IDENTITY forms, shown in the lab:

```
INSERT INTO orders (order_id, customer_name) VALUES (99, 'Hacker');
ERROR:  cannot insert a non-DEFAULT value into column "order_id"
DETAIL:  Column "order_id" is an identity column defined as GENERATED ALWAYS.
HINT:  Use OVERRIDING SYSTEM VALUE to override.
```

while `BY DEFAULT` accepts `customer_id = 1000` without complaint.

## What the key enforces by itself

No extra constraints are written, yet both of these fail:

```
INSERT INTO departments VALUES (1, 'Mathematics');
ERROR:  duplicate key value violates unique constraint "departments_pkey"

INSERT INTO departments VALUES (NULL, 'Physics');
ERROR:  null value in column "dept_id" ... violates not-null constraint
```

And the index nobody asked for is there too:

```
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'departments';

departments_pkey | CREATE UNIQUE INDEX departments_pkey ON public.departments USING btree (dept_id)
```

`UNIQUE`, `NOT NULL` and the B-tree index all come from the single words
`PRIMARY KEY`.
